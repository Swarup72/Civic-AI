# Database Migration Mapping

FRIEND_PROJECT's inferred Supabase/Postgres schema (reconstructed from the columns its client code actually references — no SQL/migration file exists in that repo to read directly, per `docs/MERGE_AUDIT.md` §4) mapped onto the canonical MongoDB schema. **No database migration was performed or is needed** — Supabase was never a data source for the merged app; this document maps *product entities*, not literal rows, since none of FRIEND_PROJECT's actual data ever existed anywhere near this merge. It exists so the *shape* of what FRIEND modeled isn't lost, and so a reviewer can see exactly what was and wasn't carried over, and why.

| Friend Entity | Final MongoDB Collection | Field Mapping | Transformation Required |
|---|---|---|---|
| `profiles` (Postgres row, 1:1 with a Supabase Auth user) | `users` (already existed; unchanged shape) | `id`→`_id`, `role`→`role`, `first_name`+`last_name`→`name` (single field, already this codebase's convention), `department_id`/`organization_id`→ *not carried* (see `complaints.claimedByUserId` below for the NGO-equivalent concept) | **REBUILT, not migrated.** `profiles` existed because Supabase Auth's user table is separate from application data; this codebase's `users` collection already merges both roles into one document (auth + profile), so there was never a second table to reconcile. No transformation script exists or is needed — new users are created directly in `users` via the existing `auth.py::register`/`backend/seed.py`, unchanged. |
| `complaints` (Postgres table) | `complaints` (already existed; extended additively) | `citizen_id`→`reportedBy`, `department_id`→`department` (string department *name*, not a foreign key — see Field Mapping note below), `severity_score` (0-100 int)→`severity` (`SeverityLevel` enum, via `llm_service._severity_score_to_level()`'s bucketing, Phase 6), `assigned_ngo_id`→`claimedByUserId` (Phase 4 — see status-vocabulary note below), `support_count`→`supportCount`, `image_url`→`imageUrl`, `address` (free text only)→`location.address` (+ required `location.latitude`/`.longitude`/`.geo`, which FRIEND never had at all) | **Not migrated — no source data existed to migrate.** The mapping above documents equivalence for anyone comparing the two schemas, not a script that ran. Two structural differences that could NOT be preserved 1:1, by design (`docs/MERGE_CONFLICTS.md` §5): FRIEND's 8-status vocabulary (`submitted, ai_analyzed, acknowledged, in_progress, escalated, proof_submitted, resolved, ai_verified`) does not map one-to-one onto this codebase's 11-value `ComplaintStatus` enum — no new enum values were added; every FRIEND status concept was mapped onto an *existing* value plus, at most, an existing auxiliary field (e.g. FRIEND's `proof_submitted` → this codebase's `RESOLVED` + `completionEvidenceUrl` present; FRIEND's `resolved` → this codebase's `CONFIRMED`, **not** its own `RESOLVED` — a naming collision documented explicitly so it's never conflated). `department_id` (a real Postgres foreign key) became a plain string field, since MongoDB documents here use string references, not enforced foreign keys, matching the existing `areaId` pattern. |
| `complaint_updates` (Postgres table — a flat, fully-visible history) | Split across three EXISTING collections, unchanged in shape: `status_history` (status transitions), `timeline_events` (typed, role-aware public/internal event log), `notifications` (per-recipient rows) | `complaint_id`→`complaintId`, `author_id`→`changedBy`/`actor_id` (depending on target collection), `comment`→`note`/`public_message`, `proof_url`→ folded into `media` collection documents (a real, validated, EXIF-aware upload) rather than a bare URL string | **REBUILT as three specialized collections, not migrated as one.** FRIEND's single flat table conflates what this codebase deliberately keeps separate: a citizen-facing history, a security audit trail (`audit_logs`, no FRIEND equivalent at all), and per-user notifications. Collapsing these three back into one flat table to "match" FRIEND would be a regression, not a merge — explicitly rejected per `docs/MERGE_MAPPING.md`'s KEEP_YOURS decision for timeline/audit/notifications. |
| `complaint_supports` (Postgres join table) | `supports` (already existed; unchanged) | `complaint_id`→`complaintId`, `user_id`→`userId` | **No transformation needed** — already structurally identical (a join-table pattern), already unique-indexed on the compound key in both systems. |
| `departments` (Postgres table, admin-managed) | `departments` (**new**, added Phase 5) | `id`→`_id`, `name`→`name` (**unique**) | **REBUILT as a new MongoDB collection**, not migrated — no source rows existed. Additive to, not a replacement for, the pre-existing fixed `Department` Python enum (`app/schemas/enums.py`), which continues to drive the AI classifier's default category→department mapping; admin-created departments are a separate, evolvable list layered on top (`app/routes/admin.py`). |
| `organizations` (Postgres table, admin-managed NGOs) | `organizations` (**new**, added Phase 5) | `id`→`_id`, `name`→`name` (**unique**), `contact_email`→`contactEmail` | **REBUILT as a new MongoDB collection.** Not yet linked to individual NGO user accounts (`complaints.claimedByOrgId` stays `None` — see below); an NGO's identity today is still 1:1 with its login account, not a real organization membership. This is an honest, documented gap, not silently glossed over. |
| `claim_complaint(p_complaint_id, p_user_id, p_role, p_org_or_dept_id)` (a Postgres **stored procedure**, not a table — its actual SQL is not present anywhere in FRIEND_PROJECT to read or port) | `app/services/escalation_service.py` (escalation) + `app/routes/authority.py::update_complaint_status`'s NGO claim guard (accept) | N/A — this was a procedure, not data | **REBUILT from its observed EFFECT only, never its implementation** (which isn't in the repo to read). The product behavior it clearly provided — "atomically claim an escalated case, preventing a double-claim race" — was re-implemented as a conditional MongoDB `update_one` (`{"_id": ..., "status": "ESCALATED", "claimedByUserId": None}`), proven race-safe by a dedicated test that exercises the DB layer directly (`test_claim_conditional_update_is_race_safe_at_db_layer`), not assumed correct by analogy. |
| Supabase Storage (`complaints` bucket — proof/evidence photos, public URLs, no EXIF handling) | Local filesystem, `uploads/public` + `uploads/private` (already existed; unchanged) | `image_url`/proof-photo public URL → `media` collection document + `publicUrl` (EXIF-stripped) + `storagePath` (private, EXIF intact, never served) | **DISCARDED, not migrated — by explicit protected-capability rule.** FRIEND's storage mechanism has no public/private split and no EXIF handling; adopting it would have been a real privacy regression (a GPS-tagged original served publicly). Nothing from Supabase Storage was ported in any form. |
| Supabase Auth (hosted JWT/session, a table this project's own client code never directly reads, only calls through the `supabase-js` SDK) | This app's existing HMAC-signed opaque token (`app/auth_utils.py`) — **unchanged** | N/A | **DISCARDED entirely.** No auth data, session, or mechanism from Supabase Auth was ported in any form — the architecture mandate forbids two competing authentication systems, and Supabase Auth's actual implementation (hosted, external) isn't something a local MongoDB migration could represent even if it were wanted. |

## What this table does NOT claim

- It does **not** claim any data was actually moved from a Supabase project into MongoDB — no such migration ran, none was requested, and FRIEND_PROJECT's Supabase project (if it still exists) was never connected to during this merge.
- It does **not** claim FRIEND_PROJECT's Postgres schema is fully known — everything Postgres-side here is *inferred* from client-side column references (`docs/MERGE_AUDIT.md` §4 states this plainly), not read from a real schema dump, since none exists in that repository.
- It does **not** imply every FRIEND entity has a MongoDB equivalent worth having — `complaint_updates`, in particular, was deliberately **not** copied as a single flat table; see the row above for why splitting it was the correct call, not an oversight.
