Measurable, testable criteria for calling the merge (as scoped in `MERGE_PLAN.md`) complete. Written in the same verified-not-assumed style as `YOUR_PROJECT/docs/acceptance-criteria.md`. Each item is checkable by running a specific command, hitting a specific endpoint, or performing a specific click-through — not by opinion. **All boxes started unchecked; this document defines "done," and is updated only as each phase's work is actually run and observed, never checked off in advance.**

**Legend, added once implementation began:** `[x]` = actually run/observed and passed. `[~]` = verified by code review and a successful build, but *not* by a live rendered check (see each phase's limitation note for why). `[ ]` = not yet attempted. A phase header is marked ✅ IMPLEMENTED, VERIFIED / PARTIALLY VERIFIED / BLOCKED / NOT IMPLEMENTED per the no-hallucination policy — never left to be inferred from the checkboxes alone.

## 7. Phase 7 — Proactive SLA escalation sweep — ✅ IMPLEMENTED, VERIFIED (pytest + live startup/shutdown)

**Design notes:** the escalation route's core logic was extracted into a new `app/services/escalation_service.py::perform_escalation()`, shared verbatim by the human-initiated route (`complaints.py::escalate_complaint`, refactored, not duplicated) and the new sweep - one escalation implementation, not two. `sla_service.find_ack_breached()` deliberately excludes any complaint that has a real `ACKNOWLEDGED` entry in `status_history`, even if it's currently `OVERDUE` — an `OVERDUE` complaint can be overdue on its *resolution* deadline after a perfectly on-time acknowledgment, which is not an "authority never acknowledged" failure and must not be auto-escalated as if it were. This distinction was deliberately tested (see below), not left implicit.

- [x] The sweep escalates a genuinely ack-breached, never-acknowledged complaint (past the grace period) — **verified by pytest**: `test_sweep_escalates_ack_breached_unacknowledged_complaint`.
